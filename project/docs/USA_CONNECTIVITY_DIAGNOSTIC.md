## Тест входа через TR с выходом США

Следующий отдельный тест: телефон -> TLS/WS на TR:2053 -> TLS/WS на США:2053
-> Xray США -> интернет. Это обход прямого проблемного маршрута, а не
исправление доступности самого американского IP из сети телефона.

На TR добавлен `/etc/nginx/snippets/hexenvpn-us-relay.conf`, подключённый
из `/etc/nginx/conf.d/hexenvpn-tr-ws.conf`. Шаблон в проекте:
`project/nginx/us-relay.locations.conf.template`.
Подстановки: `__MASTER_IP__=82.38.60.90`, `__MASTER_WS_PORT__=2053`,
`__MASTER_DOMAIN__=serghexen.ru`. Путь теста: `/api/v1/us-relay`.

Upstream фиксирован, его TLS-сертификат проверяется. Авторизация остаётся
в Xray США по существующему UUID. Обычный `/api/v1/stream` на TR не менялся.
Применён только `nginx -t` и reload nginx; Xray не перезапускался.
Бэкап TR: `/root/backup-us-relay-20260909T054335Z/hexenvpn-tr-ws.conf`.

Создана отдельная персональная подписка `/var/www/sub/test-us-tr-<токен>`
на мастере с профилем `USA via TR TEST [WS]`. Доступна через HTTPS-relay TR.
Существующие подписки, БД и конфиги Xray не менялись.
Полный туннель проверен временным клиентом: выходной IP `82.38.60.90`,
HTTPS-запрос внутри туннеля успешен. Проверка с телефона пока не завершена.

Позже пользователь подтвердил: через TR -> США сайты открываются,
но задержка высокая. Прямое подключение к США остаётся нерешённым.

Ограничения: зависимость от двух ВМ, дополнительный транзит и расход трафика
TR; серверные проверки не гарантируют доступность из сети пользователя.
Статический тестовый профиль не является постоянной подпиской.

Откат: удалить строку include только `hexenvpn-us-relay.conf` из server block
TR, выполнить `nginx -t && systemctl reload nginx`, затем удалить отключённый
snippet и конкретный тестовый файл подписки на мастере. Не восстанавливать
весь старый nginx-конфиг поверх более поздних изменений. Существующие
подключения при graceful reload могут оставаться до закрытия клиентом.

## Персональный тест WS с фрагментацией TLS

После неуспешных тестов Hysteria2 создана отдельная подписка
`/var/www/sub/test-fragment-<случайный_токен>` с профилем
`USA TEST WS Fragment`. База: существующий WS-профиль владельца
`tg_227380225`. Из параметров подключения добавлено только
`fragment=50-100,5-10,tlshello`; имя профиля заменено. UUID, fingerprint,
порт, SNI и WS path остаются прежними. Серверные конфиги не менялись.

Документированный Happ URI-параметр задаёт фрагментацию ClientHello.
Это не уменьшение MSS и не IP-фрагментация на сервере.
Эквивалентный Xray-клиент использует `sockopt.dialerProxy=fragment`
и отдельный freedom outbound с настройками:

```json
{"fragment":{"packets":"tlshello","length":"50-100","interval":"5-10"}}
```

Временный клиент проверен на мастере: HTTPS-запрос вернул `82.38.60.90`.
Контейнер и временный конфиг удалены. Выдача ссылки через TR проверена.
Это проверяет совместимость серверного WS с фрагментацией, но не доказывает,
что установленная версия Happ применила URI-параметр или что домашний
Wi-Fi пропускает такое соединение. Клиентский тест ещё требуется.
По документации Happ глобальные настройки могут перекрывать настройки
конкретного профиля; при неудаче проверить эффективный клиентский конфиг.

Профиль статический, персональный, не для массовой выдачи. Откат:
удалить конкретный тестовый файл и дополнительную подписку в приложении;
рабочую подписку не удалять, сервисы не перезапускать.

Источники:
[Happ URI-параметры](https://github.com/HappDev/happ_su/blob/main/dev-docs/examples-of-links-and-parameters.md),
[Xray Freedom fragment](https://xtls.github.io/en/config/outbounds/freedom.html).

### Результат наблюдения и TCP Split

Скриншоты пользователя подтвердили импорт параметра в Happ FinalMask.
Во время согласованной проверки Wi-Fi TCP-соединения до США устанавливались,
клиент отправлял данные несколькими фрагментами. Это подтверждает отправку
фрагментированного TLS, но не успешность туннеля. Краткий дополнительный
разбор в памяти зарегистрировал неполные ClientHello в нескольких потоках
и 1428 байт данных от сервера суммарно. Захват ограничен по времени/числу
пакетов, поэтому нельзя по нему уверенно назвать причину отсутствующих
данных или утверждать, что все соединения одинаково блокируются.
Содержимое пакетов не сохранялось. Наблюдение завершено.

В ту же персональную тестовую подписку добавлен второй профиль
`USA TEST WS TCP Split`: вместо `tlshello` используется `packets=1-3`,
то есть дробление первых трёх TCP-записей, без разбиения ClientHello
на дополнительные TLS records. URI: `fragment=50-100,5-10,1-3`.
Первый профиль сохранён. Эквивалентный Xray-клиент прошёл HTTPS-проверку
с выходом `82.38.60.90`; применение в Happ требует клиентского теста.
Серверные конфиги и основная подписка не менялись.
Бэкап тестовой подписки: `/root/backup-fragment-test-20260909T064119Z`.
